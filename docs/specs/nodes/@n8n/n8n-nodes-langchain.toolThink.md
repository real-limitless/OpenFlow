## Wire format

- **Type string:** `@n8n/n8n-nodes-langchain.toolThink`
- **Aliases:** (none)
- **Inputs:** (none — invoked by the connected AI agent at tool-calling time)
- **Outputs:** `ai_tool` × 1
- **Credentials:** (none)

This is a LangChain **tool sub-node**. It connects to an AI agent root node through a single `ai_tool` output and is exposed to the model as a callable tool. It receives no independent `main` data input and performs no external I/O.

## Parameters

| name | type | default | required | notes |
|------|------|---------|----------|-------|
| `name` | string | — | yes | Callable identifier exposed to the agent (letters, digits, underscores) |
| `description` | string | — | yes | Free-text guidance telling the model when to invoke the tool (e.g. for complex, multi-step questions before answering) |

The node adds no functional data parameters: it exists purely to expose a "thinking step" to the agent. A static connection hint (notice) is shown in the UI when the node is not yet wired to an AI agent; it has no runtime effect.

## Runtime behavior

### Input

The node has no `main` input connection. The connected agent invokes it during tool-calling. Expressions in the tool's parameters resolve against the **first item only** of the calling context (standard sub-node semantics); they do not iterate per-item.

### Invocation

When the model calls the tool, the node responds with a prompt inviting the model to reason through the problem out loud before producing its final answer. It does **not** fetch data, change state, or call any external service. The model is expected to reflect and then continue with its answer.

### Output

The tool's response to the agent is a short message instructing the model to think the question through step by step. The model's subsequent (self-contained) reasoning and final answer are generated by the agent; the tool contributes no data to the workflow output.

### Errors

The tool has no external dependencies, so invocation failures are limited to expression-resolution errors in its own parameters. Standard `continueOnFail` behavior applies: when set, a resolution failure yields an error payload to the agent instead of aborting the run.

### Expressions

`name` and `description` accept n8n expression strings.

## Acceptance tests

### Test: exposed as a callable tool with metadata

**Given** a connected AI agent and a Think Tool configured with `name` and `description`:

**Parameters:**
```json
{
  "name": "think",
  "description": "Use this tool to think carefully about a complex question before answering."
}
```

**Expect** the agent's tool schema exposes a callable named `think` whose description matches the configured text, and no other tool parameters.

### Test: invocation produces a thinking prompt, no side effects

**Given** the tool is connected to an agent and the model invokes it:

**When** the model calls `think`:

**Expect** the tool returns a message inviting the model to reason step by step. No external service is contacted, no data is persisted, and the model continues toward its final answer after receiving the prompt.

### Test: complex-question flow

**Given** a riddle-style question (e.g. a multi-person relationship logic problem) where the naive answer is uncertain:

**When** the model runs with the Think Tool available:

**Expect** the model calls the tool before answering and then produces the correct, explained answer. (Functional outcome; the tool merely enables the reasoning step.)

### Test: continueOnFail on bad expression

**Given** an invalid expression in `description` and `continueOnFail` enabled:

**Expect** the tool call resolves to an error payload handed to the agent rather than aborting the workflow.
